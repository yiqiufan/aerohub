# RACER PC 双机可靠性：最小验收清单与运行安排

当前 PC 交付见 [双机运行与验收](PC_DUAL.md)。下文保留此前版本的记录。

本清单对应 ForestScene PC 双机完整探索版本 `0.2.0-forest-complete.20261119`，交付元数据 revision 1。制定计划时的状态为**离线定位完成、后续验证待执行**。原两轮飞行结果保留，整体仍为 partial；本页没有宣布修复、追加飞行通过或完整故障矩阵完成。

## 第二轮记录缺项的离线结论

直接原因已定位到诊断 rosbag2 的内部缓存丢失，而不是仅根据读回失败猜测。对两轮四个 bag，以 SQLite 只读方式遍历全部消息，按 `(topic, wall reception timestamp)` 对账 receipts；本轮键无重复，bag 无额外未记账消息，四个 SQLite quick_check 均为 ok。

| 运行/车辆 | receipts 与 writer API 计数 | SQLite 消息数 | 缺失 | rosbag 缓存告警 |
|---|---|---|---|---|
| 第1轮，两机 | 各自一致 | 与各自 receipts 一致 | 0 | 0 |
| 第2轮 Drone0 | 一致 | 与 receipts 一致 | 0 | 0 |
| 第2轮 Drone1 | 96564 | 92086 | 4478 | 4478，逐话题与缺失数一致 |

Drone1 的缺项覆盖 21 个话题，包括原生 plan 2 条、执行状态 3 条、AS2 轨迹参考 101 条、TF 1965 条、clock 555 条，以及图像、地图与状态消息。这里描述的是**诊断订阅副本**缺失，不代表控制链发布或消费了同样数量的错误消息。

缺项分布在记录器启动后约 144.51～238.17 秒；按 0.5 秒间隔分组得到 16 个观测窗口（分组仅用于分析，不是验收门槛）。最后缺项距离记录器结束还有 10.65 秒，随后仍有 3285 条成功落盘。按最近一条工作站任务事件的墙钟时间对齐，3551 条处于 tracking，927 条处于 landing；该分类具有采样误差，但足以排除“仅退出时尾部未排空”的解释。缓存告警是在关闭时汇总打印，不能把打印时刻当作丢失时刻。

应用层 queue 丢弃为 0，峰值仅 21/128；`recorder-result.json` 的 pass 为 true，因为它只检查线程错误、应用队列丢弃和 received==written。实际 `written` 在 `SequentialWriter.write()` 返回后递增，该返回没有成为实际落盘确认。因此本轮“记录器 pass”未覆盖内部缓存丢失；正式读回失败正确保留，不能放宽读回判据。

已有 ROS 读回确认缺少 plan 33、36；独立 `adapter-events.jsonl` 仍有两条完整 `native_plan_received` 消息及各自 `active` 事件，全轮 38 条原生计划均有接收/激活事件。可以用这份独立证据继续分析轨迹，但不补写旧 bag，不改写旧记录完整性结论。原 `all_cdr_messages_decode` 检查名同时包含计数一致性判断，本次缺项并非 CDR 解码异常证据。

代码依据：[诊断记录器](../../../../src/planner/racer/ros2_adapter/multi/diagnostics.py)、[读回检查](../racer_multi_ground/verify_diagnostics.py)、[飞行记录关联](readback_flight.py)。机器摘要见 [recording-gap-analysis.json](recording-gap-analysis.json)，逐条对账与原始文件哈希位于 `log/racer-ros2/20261119-recording-gap-offline/`。本次未改这些运行代码。

尚未确定的是内部缓存为何不能及时排出：现有日志缺少当时的存储延迟、缓存占用和宿主资源竞争数据。最大已记录单消息约 1.23 MB，低于本例 32 MiB 缓存；仅凭此和应用队列低水位不能确定宿主磁盘、Docker 挂载或某个线程是根因。下一步需同源双路载荷的隔离写盘对照。

## 最小验收清单

这是当前 PC 阶段的下一组必要检查；不取代 AeroHub 的完整适用矩阵。未纳入的板端、四机、跨版本回退、桥/定位/时钟故障等仍保留原状态，不因本表变成“不适用”或“已通过”。既有范围、速度、输入新鲜度、停止及降落预算保持不变；故障用例单独声明变化。

| ID | 检查与触发 | 成功判据及必须保留的证据 | 当前状态 |
|---|---|---|---|
| R0 记录完整性 | 先隔离双路真实 CDR 载荷写入；候选通过后带入正式双机全流程 | 分别对账接收、应用排队、writer API 提交、关闭后 SQLite/ROS 解码读回；无未解释丢弃；计划与查询关联成立。告警、退出码和缺失明细均保留 | 第二轮失败；缓存丢失已离线定位，未修复 |
| R1 正常完成与重复启停 | 同一候选、同一 ForestScene 配置，干净会话完成完整探索；准备补两轮，先一轮通过再复验一轮 | 两机原生自然结束、真实运动/协同/下游消费沿用已有检查；停止、原生 Land、新鲜 landed/disarmed；全部所属进程退出，记录读回通过。若后续改动改变行为，明确哪些结果需重验 | 原版本两轮功能通过，记录只首轮通过；修复候选待执行 |
| R2 主动取消 | 两机进入 tracking 且各有真实 active 后，只向本轮工作站 mission 发送受控 SIGINT | 任务保留 cancelled/未完成，不假装 native_finished；两机执行停止、降落和落地解除武装；取消不跳过恢复，证据与清理可核查 | 现有入口支持，真实注入待验证 |
| R3 探索预算耗尽 | 独立用例将探索预算设为原短程使用过的 20 秒，其他飞行参数不变；只有超时实际触发才算覆盖 | 保留 budget_exhausted/未完成或对等机因同伴失败退出；两机按既有流程停止降落。若自然完成先发生，该轮不算超时注入通过 | 实际方法/分支有隔离测试；真实注入待验证 |
| R4 单机输入中断 | 精确暂停一机本轮 RACER inputs 子进程；保持 /clock、PX4、AS2 权威状态与任务链路 | 既有新鲜度检查实际触发，任务不得自然完成；另一机联动恢复；保存暂停、检测、恢复进程和停止/Land/landed-disarmed时序。清理前恢复被暂停进程，不能让挂起进程阻塞清理 | 故障注入入口待隔离验证；未安排直接空中尝试 |
| R5 原生算法退出 | 精确终止一机本轮原生探索子进程，保留 Adapter、AS2/PX4 与监督器 | process_failure/监督故障被观测；不能等待已退出算法产生 FINISH 而跳过降落；执行层停止和两机恢复单独取证。原生 FINISH 缺失、预期非零退出不得被抹去 | 恢复分支存在；注入入口与真实恢复待验证 |
| R6 接触观测覆盖 | 先离线核查、再地面验证不会消费/清除仿真碰撞状态的接触观测来源，附加到上述正常/异常用例 | 分开报告探索、停止、降落阶段的观测覆盖；飞行障碍碰撞与正常地面接触分开，保留事件对象/时间/位置。无事件流时不报告全程无碰撞 | 当前 observe.py 只取位姿/运动/GPS/气压，没有碰撞事件；全程碰撞结论未覆盖 |

故障试验的任务 `pass=false` 或预期子进程非零退出，可以是正确的受控失败表现；必须另有故障用例报告证明“注入确已发生、检测正确、停止/降落恢复满足约定、清理完成”。不能直接以正常任务评估器返回非零判定整个故障试验失败，也不能把故障试验写成正常探索通过。R5 中死亡算法无法提供 FINISH，需要保存明确失败原因并验证下游停止和落地，不能伪造停止反馈。

历史 inputs `-11` 在 R1 及所有收尾中持续检查实际子进程退出码；若再出现，保存进程身份、日志和可得的堆栈，暂停后续飞行并定位。没有重现时只报告本轮正常退出，仍保留历史根因未明。此清单不要求通过无限重复去证明长期零故障。

## 后续运行安排与进入条件

1. **先做离线写盘对照。** 复用已有真实载荷回放方法，使用当前完整探索的两机现存消息、原接收节奏与目标存储位置，记录消息/字节速率、应用队列、内部缓存告警、读回和退出；保持网络隔离，不连接 UE/PX4。原 bag 缺失的载荷不凭空重建，回放输入清单标注这个限制。先复验原设置，再选择有证据支持的最小写入策略改动。此前缓存关闭的短地面压测已失败，不能直接把 cache=0 当作修复；单纯扩大缓存也不能未经验证就当成解决。
2. **隔离验证候选和故障入口。** 记录器应能区别提交成功与落盘完整；检查名与结果应准确反映解码/计数两个层面。R2～R5 的拥有关系、目标 PID、注入标记、取消与恢复收口先在无运动环境验证。R6 必须先确认观测无干扰，不能直接恢复轮询清除型碰撞接口。
3. **再做真实地面检查。** 候选身份明确后，用新 ForestScene 会话验证双机输入、记录、停止/退出与清理；这一阶段不解锁、不起飞。需要 UE 操作时再具体通知操作者，不提前要求刷新。
4. **按依赖执行飞行。** 先一轮正常完整探索；记录与退出均通过后，按 R2、R3、R4、R5 各一轮有界故障验证，逐轮检查恢复和下一轮前置状态；最后补同配置正常复验。发生未确认落地、非预期崩溃或无法解释的状态时停止扩展，保留基础链路并定位。只执行已完成隔离准备的用例，不把“列入计划”视为入口已可安全运行。

这不是长时间优化或算法效果评分计划，不修改 RACER 的探索策略、覆盖率目标或控制门限；也没有设置新的“越远越好”运动判据。关于探索质量，仍单独保留“原生结束不等于全场景覆盖”的边界。
