# 仿真端到端验收与证据交付

## 拓扑与职责基线

全部 Library、算法与 Demo 遵循[四方部署职责](../../docs/项目简介.md#deployment-roles)：仿真器、飞控、算力与工作站分别标明实际设备、进程和接口，允许 PC 共置。部署层先启动能力并确认就绪，工作站任务经 ROS 调用；仿真真值评分留在仿真器/工作站侧。记录现有拓扑相对该约定的差异，不以某个 Demo 参数或单次成功代表所有项目已迁移。复用固定共享镜像，组件依赖、算法和 Adapter 在派生镜像构建阶段编译；验收运行时不挂载宿主源码 workspace 或 build/install overlay，只允许独立的运行时生成配置与证据目录。

## 先定义成功

Inference 服务验收分层记录：独立环境加载、与迁移前固定输入的候选/评分一致性、HTTP 输入和忙时语义、实际 DDS→ROS Adapter→HTTP→模型往返，再到 GPU/真实传感器与下游消费。可复用 `deployment/inference/tests/` 的公共 runtime、选择逻辑和 AS2 基准入口；模型专属 ROS smoke 在模型接入时交付。CPU 合成测试不替代 GPU 或 AirSim 验收。客户端取消测试应确认底层计算结束前不会释放 worker 的忙状态。

地面站调用 onboard 能力的通信基准先用 `deployment/inference/tests/cross_container_baseline.py`：固定地面站镜像局部生成 onboard 规范查询类型，调用实际原生 AS2 Platform 的只读 ListControlModes。按该拓扑验收 Inference 时，ROS 客户端与 Adapter 必须在不同容器中，记录两端镜像/overlay、DDS 网络与 worker 所在位置；同一 ROS 测试进程构造 Adapter 仅算合成接口证据。原生 AS2 基准通过不自动证明 Inference 通过，单宿主 Docker bridge 也不等于跨物理设备验证。

读取用户目标、组件能力、接口契约和仿真配置，运行前确定场景、链路、指标、阈值、时长及需要重复的次数。来源可以是用户要求或明确标注的工程验收建议；缺少关键指标时先明确，不能看结果后降低阈值。

输出分为通过、失败、未覆盖；缺证据不得记为通过。编译、接口测试、合成输入冒烟、真实数据回放、仿真闭环和真机验收是不同证据等级。

用户决定保留某个已验证配置作为阶段性交付时，将默认入口、README与验收摘要对齐
到该配置，明确目标速度与实际速度、单轮与重复可靠性。旧实验入口可移除，发现、
分析、失败与原始证据必须保留；未完成项不得因分支整理重判通过。正常任务局部
通过不关闭故障测试，也不代表整体复现成功；后续专项方案仅作为待实现问题记录。

每个指标同时写明统计窗口和实际门控阶段，核对正常执行、停止和降落/恢复分支是否都检查它。任务退出0或结果pass不能替代未受监控阶段的指标结论。补充分析发现原检查遗漏时，保留原任务结果与补充检查的不同结论，标明阶段缺口，不追改清单或放宽门限以统一为通过。

“复现成功”是对完整适用测试矩阵的结论，不是对某一层测试的别名。运行前建立矩阵，至少逐项判断源码与依赖构建、真实算法运行、ROS/AS2 接口、平台真实传感器输入、实际下游消费、正常场景指标、故障/恢复和资源清理是否适用；涉及运动或平台链路时纳入有屏 AirSim + PX4 SITL 闭环。只有所有适用项在同一可追溯源码/镜像版本上执行并通过，且下述证据包齐全，才能报告复现成功。

当前开发主机具备可用 NVIDIA GPU。依赖 GPU 的算法必须以真实 GPU runtime 处理目标输入并验证输出；`nvidia-smi`、CUDA 可见、库导入、镜像构建、CPU mock 或合成算法输出均不算 GPU 算法测试。不得把 GPU 项标为可选或因预计耗时而跳过。

主机 GPU 可用不等于 Docker GPU runtime 可用。验收前同时检查 NVIDIA Container Toolkit/CDI、Docker runtime 和容器内真实 CUDA 算法执行。显式挂载 `/dev/nvidia*` 与主机驱动库可用于隔离 Toolkit 缺失问题，但只属于诊断路径；除非部署清单明确支持并完成同等复验，否则不能据此宣称标准 Compose 可部署。诊断通过后仍应保留缺失前置条件和正式恢复入口。

任何失败、skip、未执行、超时无结论、证据缺失或安全门阻止都使总体结论保持“复现未成功/未完成”。可以准确报告已通过的层级，但不能用“部分成功”“基本成功”暗示完整成功。外部条件确实缺失时保留未完成状态和恢复入口；条件恢复后继续原矩阵，不事后缩小声明范围。

真机验收只在用户目标、能力声明或交付范围要求真机时纳入成功矩阵。项目统一的 AirSim + PX4 SITL 验收不是因已有 GPU 而被真机要求替代。

ROS 测试可能捕获 ImportError 后用 skipIf 跳过全部消息转换检查，最终仍显示 OK。执行接口验收前显式导入目标消息和实际 Adapter，检查通过数与跳过数；纯数学测试通过不能替代 ROS 转换测试。缺少算法应用镜像时，可在已记录版本的兼容工具链中编译当前消息与适配包、运行转换和节点构造检查，但只能报告这些包的构建及接口证据，不能声称完整算法镜像或仿真链路通过。隔离网络的构造检查也不能证明 DDS 与真实下游连通。

## 合并后全量验收的范围核对

用户要求覆盖所有集成工作或上游额外修改时，从当前源码、补丁、启动入口和两侧分支差异建立覆盖矩阵，逐项关联运行配置与证据。区分补丁中的上游版本更新和项目新增行为。源码树一致只能证明补丁重放完整，不能证明功能正确。

执行前核对入口实际选择的 backend、机数、ROS 版本和计算拓扑；Demo 名称不证明走的是 FollowTimedPath，旧单点参考与新 Behavior 链路须分别标记。需要板卡的混合部署不能直接记为 PC 仿真已覆盖。用户指定仿真后端时，不用另一个后端的历史结果替代。

首次接管被连续性检查拒绝时，对照实际状态和原生轨迹首点，优先用固定输入驱动真实算法节点复现；原生发布者可能采用 BEST_EFFORT，回归订阅需匹配。SUPER 的非占据位置曾被量化到栅格中心，产生超过执行门槛的首点偏移；应修正不必要的边界移动并验证原占据搜索仍保留，而非放宽连续性阈值。合成回归通过后再执行完整仿真。

先检查场景可执行文件、图形设备/渲染器、运行镜像和子模块是否真实可用。场景资源与镜像可能不随源码提供；下载成功不证明可启动。冻结本次源码与镜像映射，发布镜像或其他 worktree 的编译产物只能作为明确记录的依赖，不能冒充当前源码重建。

## 按任务选择验证分支

- 取消、落地超时、执行拒绝或停止后重新规划异常：读取[执行诊断](references/execution-diagnostics.md)，按相关阶段补证据，不把全部排查项作为每次迁移必做项。

记录关联和正常等待的案例见[验收案例](references/validation-cases.md)。

诊断前先明确可观察的任务问题和待区分的原因：接口不兼容、输入/地图不正确、执行交接失败、任务到时或算法原生等待等。正常休眠、无可用视点、重试本身不是失败判据；核查其是否导致既定任务无法继续或违反契约。任务时间到了也不能证明探索已完成。

优先用已有记录定位触发条件和影响；只有缺少判定所需证据时才补最小记录或安排针对性复验。若行为符合原契约且未影响本轮要求，记录边界后返回迁移主线，不为消除正常状态增加算法策略或无限重复飞行。尚未执行的原验收项仍保留，不能借此删减矩阵。

## 按能力建立完整链路

云端视觉导航分开验证小图 API、原算法 prompt/解析、跨容器 Function 消费、实际
相机输入和运动执行。地面调用时延通过不保证飞行时仍满足图像结果年龄门；保留
原采集 stamp 和既定 freshness，记录过期拒绝。timeout/取消/降落通过但零轨迹执行
只证明生命周期收口，正常导航用例还须有实际 Behavior 消费与运动证据。可在事先
声明的有限预算内重试新场景，不通过放宽年龄门或替换模型消除失败记录。
用户明确要求调整门限时，将新值作为独立实验配置快照保存，运行中读取实际参数确认生效，
保留原门限失败结果；新结果只适用于新配置，不追溯改判旧用例。

预检采样为空时先发现实际话题名、类型和 QoS；PX4 的版本化话题（如
vehicle_status_v4）可能与旧探针不同。空样本既不是预检通过，也不是飞控预检失败。

| 能力 | 必须覆盖的消费链与指标示例 |
| --- | --- |
| Planner | 场景与目标→真实规划算法→Adapter→Behavior→控制/平台→模拟运动；检查到达、约束、碰撞、多机时间协调 |
| Behavior | 实际 Goal→执行组件→控制/平台→模拟运动→完成反馈；检查跟踪、取消、更新、失败收口 |
| 状态估计 | 仿真 IMU/图像/点云→真实算法→原生插件→导航/控制实际消费→模拟运动；比较真值误差、延迟、漂移与失效行为 |
| Perception | 仿真传感器→真实算法→环境接口→实际查询/规划消费者→可观察任务结果；检查表示、覆盖及下游功能 |

真值用于评分，不得通过隐藏的真值定位源替代被验收算法。定位可先做影子运行，确认精度后再进入仿真控制闭环；影子运行不能记为闭环通过。纯感知能力不强制产生运动，但必须验证实际消费者；声称导航地图可用就需导航消费证据。

FAST-LIVO2 的合成三传感器冒烟和插件契约测试属于输入/接口级证据。只有 AirSim 实际 IMU、图像、点云进入真实算法，再由状态与感知输出被下游消费，才可记为该算法的 AirSim 闭环；AS2/PX4 的其他飞行 Demo 不能替代这条证据。

状态估计进入权威控制前必须设置 shadow gate。先让已验证的定位源控制飞行，候选估计器只输出状态并与真值比较；门限应在运行前固定。shadow 失败时，authority 场景必须记为“未执行（安全门阻止）”，不能为凑齐测试项强行切换状态源，总体复现结论也必须保持未成功。失败测试仍应完成受控降落、解除武装、证据导出和资源清理。

shadow 的精度、覆盖率和输出间隔通过后，还要核对权威 TF 每一段的更新率与控制器 freshness。低频全局定位不应直接替换高频 `odom -> base_link`；需要双速率分层时，分别测量全局校正、本地状态和 canonical 输出的唯一 stamp 频率，并执行最小 Takeoff/GoTo/Land 后再跑完整 authority 场景。门限结果用版本化脚本逐项生成 machine-readable pass/fail，不能只保存指标 JSON 后人工宣称通过。

故障测试按分层职责注入：停止全局算法时验证全局校正停止更新、本地 canonical 状态保持所需频率并完成受控降落；这不替代本地估计器故障测试。连续飞行用例之间若平台拒绝模式重置，必须按拥有关系完整重启 AirSim、PX4、桥、算法和 AS2，保留被会话残留阻止的失败尝试。

## 执行与故障恢复

1. 检查仿真传感器能否提供算法所需扫描类型、逐点时间、图像和同步标定。无法满足时记录输入不适用，不把 mock 算法或真值冒充输入补齐。
2. 隔离测试命名空间、ROS domain、端口、仿真实例和输出目录；不停止无关部署。确认权威状态、TF 和时钟源没有竞争发布。
3. 先跑正常场景，采集真实算法输出、AS2 接口、下游订阅、控制指令与运动结果，证明实际使用的是目标能力。
4. 在隔离仿真中按风险注入数据中断/延迟、算法退出、桥断连和定位重置等故障；运动组件再检查取消、停止确认和控制权交接。记录预期停止或恢复规则，重启成功不自动等于状态连续性安全。
5. 自动评估并保留失败证据。测试结束只清理本次创建的资源，确保没有残留发布者。异常恢复仍未验证时明确列出，不宣称全部成功。

故障检测延迟从故障注入已经生效的证据时刻算到消费者观察到失效的时刻，不能用“当前时间减最后一条消息时间”替代；后者包含注入前已有的消息年龄，只能作为输入陈旧程度的诊断。注入器与消费者分进程时保存注入标记及墙钟时间，并同时记录输入消息时间、失效观察、拒绝服务和恢复后的新样本，避免因轮询或文件握手把检测延迟算错。

PX4 SITL 与锁步 AirSim 的连接状态跨容器重启不一定自动恢复为干净初始条件。若前一轮留下 armed/offboard、异常世界更新或 TCP 会话状态，下一轮应按拥有关系受控停止并重启本轮 AirSim、PX4、桥和 AS2，再重新验证传感器、时钟、preflight 与 disarmed 状态；不能仅重启 PX4 容器后把陈旧场景状态当成新一轮证据。

滚动规划器的故障结果可能受当前轨迹剩余时长影响：算法进程退出后，执行侧可能先报告
替换轨迹超时、覆盖期限耗尽或 Behavior 失败。验收器必须先用进程身份或退出状态证明
注入的算法确已停止，再检查预声明的允许终态、停止确认、降落、解除武装和清理；不能
仅凭某条错误文字判定故障处理通过。终止 ROS CLI 包装器时必须覆盖其拥有的完整进程组，
避免包装器退出但算法节点仍存活。

规划任务的空间边界只评估任务实际开始到结束的样本；起飞前、任务停止后的降落样本
应单独受平台安全门约束，不能混入任务路径范围后制造假越界。轨迹验收分别检查碰撞
净空、空间边界、滚动位置/速度/加速度/偏航连续性以及配置的速度和加速度上限。
碰撞安全不等于动力学可执行；失败时记录具体谓词与两侧 P/V/A 数值，不通过放宽门槛
掩盖算法或重定时缺陷。

### 落地超时的证据分解

分别定位降落命令被接受、ground_contact、maybe_landed、landed 和解除武装的时刻；按日志内固件版本读取实际检测条件，确认是测量、状态、控制输出还是等待逻辑未满足。先核对已有门限及其用途，只在有实测依据时适度调整，不为迁移复现附加原任务不需要的优化指标。

运行及重启后核对实际logger/backend和新日志是否产生；旧日志、渲染位置或最终disarmed不能补齐本轮缺失的检测输入。固件字段含义、反馈顺序与停止后重新规划按需阅读[执行诊断](references/execution-diagnostics.md)。观测副作用与场景输入核查见[AirSim参考](../uav-platform-sensor-adaptation/references/airsim-px4.md)。

## 必须交付的证据包

对测试自行启动的 ROS launch，使用独立进程组管理生命周期，容器按需启用 init 回收孤儿进程。清理须有界并检查子进程；仅 wait 启动器可能无限等待，启动器退出也不证明节点已退出。先正常中断，必要时再对本次拥有的进程组升级终止信号，保留升级记录；不能按通用进程名杀掉其他部署。将业务断言结果与清理结果分别记录，手动停止导致的非零退出不能报告为完整测试正常结束。

在 `log/<任务>/<运行标识>/` 保存：

- 运行清单：源码提交及 dirty diff、镜像 ID、场景、参数、种子、软件/硬件版本、执行命令。
- 连接证据：实际节点、插件、话题发布订阅与 TF/时钟源，证明没有旁路替代。
- 可重放记录：适用的 bag、平台日志、任务请求与反馈、真值和故障注入时间线。
- 评估报告：每个指标的预设阈值、计算方法、实测值、通过/失败、缺失数据处理；附误差曲线、轨迹或地图可视化，任务视频作为辅助而非唯一证据。
- 工件索引与校验和、复验入口、未覆盖项。报告不依赖口头描述；若数据过大，说明保留位置和获取方式。

“启动命令没有显式源码挂载”不足以证明容器自包含。容器启动后必须 inspect 本轮每个实际
容器的 mounts，按容器记录 type、宿主 source、容器 destination 和读写属性；只允许预声明的
运行时生成配置与独立证据目录，出现仓库、源码 workspace、build/install overlay 或依赖目录
立即判失败。每个用例保存 mount 清单，并在清理后另存 owned 容器不存在、场景停止等结果，
不能仅凭 runner 正常退出推断资源已收口。

将原始失败、定位用例和修复后结果关联到不同版本/镜像，避免后轮成功覆盖前轮失败。observe 策略下任务完成与约束满足分别判定：例如无越界观测并不代表速度上界也通过，备用标志计数也不等于独立切换次数或受控故障验收。原始日志可被忽略，精简验收摘要应受版本管理或提供固定可获取引用。

过程与证据索引写入 `skill/temp/<任务>/`。最终报告包含测试矩阵，每项注明适用性、命令/场景、证据、结果和对应源码/镜像；任何适用项未通过时不生成“成功”报告。若验收条件缺失，交付已完成层级、缺口和下一步。完成后更新有关 Skill。

## 记录链自身的完整性

新增或扩展图像、点云、状态等诊断记录时，先确定实际消息类型、载荷尺寸/速率、存储位置和需要配对的采样窗口。分别保存订阅接收数、应用队列丢弃数、提交写入数，以及关闭并排空缓存后的实际读回数；用匹配消息类型解码并按原始 stamp 核对配对载荷。进程退出正常或缓存接收成功不证明全部落盘；零应用队列丢弃也不证明 DDS 无传输丢失。发布者图快照与逐消息来源信息分别标注。

记录吞吐不足时，先区分传输/QoS、回调、队列和存储瓶颈，再用同一真实载荷及接收节奏做隔离前后对照。批量缓存或独立存储是可选实现，选择依据是实测吞吐、资源、丢弃与收尾结果，不固定某个案例的缓存大小；不静默抽样或修改算法输入频率来换取“记录完整”。保留原失败及修正后的读回报告，标明测试位置和负载范围。

话题完整录制与算法实际消费分别取证：原始消息、适配后的消息、内部地图更新/查询可能具有不同频率。需要解释规划或感知行为时，用算法侧更新时间、序号或查询记录关联实际消费，不能仅凭 bag 有数据宣称算法已使用。地面记录与离线回放通过只证明相应采集/存储链，空中负载和动态行为仍需原适用矩阵验证。

需要将消息与算法内部状态关联时，先检查关联键在同一车辆、进程会话和时间域内是否唯一。相同header时间戳可能对应多次发布或多个地图版本；不能以字典覆盖或最近匹配隐藏歧义。记录可确认的关系、重复项和无法判断的范围。若选择增加序号/版本标识，须验证它贯穿实际发布与读回路径，不能把尚未验证的方案写成既定修复。

新增生命周期诊断时，分别验证请求发出、执行反馈和状态应用等真正发生的事件；记录函数单测不能证明所有调用分支都触发。不要用早期某次停止快照代替最终停止确认。具体入口覆盖按[AS2接入](../as2-extension-integration/SKILL.md#繁忙规划器的停止反馈)核对，结果独立于运动通过与否报告。

新增记录保持原算法判断与输入频率；用相同输入核对开关前后输出和已声明的行为，随后按需检查真实负载下的记录完整性与收尾。单次飞行通过不证明零开销；未测得时延或资源影响时明确未验证。记录故障与运动故障分别列出，但适用证据项未通过时仍不得宣称完整验收通过。

## 当前经验范围

FAST-LIVO2 已完成 AirSim 1.8.1 真实 IMU/图像/LiDAR 的有屏 shadow、AS2 authority、传感器中断和算法退出矩阵。shadow 通过预设 `0.5 m` 门限后，候选状态作为唯一 AS2 状态/TF 权威完成 Takeoff/GoTo/Land；故障用例在空中真实停止容器，并以 PX4 降落、解除武装和资源清理作为通过条件。该结论不包含 PX4 外部里程计融合、真实数据集或真机。

此案例还表明，算法输出持续、点云非空和任务由另一定位源安全完成，都不能替代候选状态精度。对多模态估计器应分别记录输入消费、内部状态、shadow 精度、权威切换和故障降落；任一适用项缺失都不能声称完整闭环成功。PX4 的 `Ready for takeoff!` 日志不等于真实 preflight 通过，应订阅目标版本 `VehicleStatus.pre_flight_checks_pass` 并要求稳定窗口。AirSim lockstep 的 PX4 TCP 断开后可能使场景退出，重试必须重启本轮完整 AirSim/PX4 链，而不是只重启 PX4 容器。

PC 编排、板端执行的链路需分别记录算法镜像、目标安装 manifest、DDS 网卡与 peer、domain、PX4 system ID 及进程身份。任务退出前以停止反馈和降落解除解锁确认作为清理门槛；结果缺失或恢复未确认时保留执行端、时钟和仿真，交付其状态及恢复方法。端口占用和其他实例的存在分别检查，Docker 无法访问时不得把 inspect 失败当成资源空闲。

Fast DDS 显式 initialPeersList 用于混合部署时，应同时包含跨机 peer 和本机可达地址。仅指向远端可导致本机容器间图发现/数据缺失；白名单增加回环地址本身不能补齐 peer。先用无运动探针测量 `/clock` 的实际消息数，再进行地面数据和 TF 权威核查。2026-11-09 的 SUPER 检查中，本地 peer 探针五秒收到 251 条时钟；这只证明发现/传输修复，不等同飞行闭环通过。

多参与者发现还需保留域内 multicast discovery 或显式覆盖全部 participant 端口；只恢复 clock 参与者不能证明导航和规划节点也互相发现。地面验收要求真实 SUPER 地图输出而非仅进程存活。

混合部署共用 `/clock` 不代表 PX4 控制消息的系统时钟已同步。当前 Pixhawk 兼容补丁使用系统时钟填 PX4 控制消息时间戳，运行前沿用既有 0.5 秒墙钟偏差门槛。偏差超限时保留测量并拒绝飞行；系统对时影响设备上的其他时间敏感服务，明确获得授权后才能执行现有临时 sync-time，再做最小 Offboard 回归。2026-11-09 曾观测约 -2.77 秒偏差及 PX4 命令 176 临时拒绝；随后同一历史混合入口的 short-02 已通过，但尚无隔离变量的因果对照，不能把先后相关性写成已确认根因或持续同步可靠。

时钟异常区分初始偏差、持续频率漂移与系统服务调时造成的跳变。使用
`deployment/robopi/diagnostics/clock_probe.py` 同时记录两侧墙钟、单调时钟和 HDC
往返区间；结果中的 RTT 上下界覆盖偏差变化时，不报告确定的漂移率。墙钟/单调
时钟差只能识别跳变，不能排除共同频率校正。短观测未见跳变不等于排除间歇故障。

SUPER 混合入口现已在运行中复查既有时差门槛，超限请求任务停止与降落恢复，
保留 clock-offsets.jsonl；这属于有延迟的编排层检测，不等于控制消息级硬保护。
`test_runtime_skew_is_detected_after_initially_valid_clock` 已确认旧实现漏报、修复后
检出；该测试注入测量结果，不调整设备系统时钟，也不证明真实时钟故障下飞行恢复。
同步后的短程通过仍须与长期漂移可靠性分别报告。

## 到达门槛与停止验收分开

视觉速度策略可能没有终点保持语义。先核对官方结束条件；若任务要求停在终点，
在实测首次入圈后停止策略并等待执行退出，再由已有位置 Behavior 接管原任务目标。
只取消并悬停可能停在制动后的位置，不能据此推断仍在目标球内；等待策略自行低速也
可能导致盘旋。交接方案在真实闭环通过前保持待验证。记录交接位置、终点 Behavior
速度参数、停车阶段位置/速度/状态年龄及仿真和墙钟时间，分别判定入圈、最终距离、
低速连续时长、总停车预算、碰撞与降落。超时前最后一帧速度很低不代替完成连续保持。
失败后调整倾角等验收门槛的轮次仅作诊断；保留原门槛下的失败，另行预声明正式复验。

与既有Demo比较停车能力时，逐项核对计时起点、时钟域和预算用途。导航到达与
低速保持、物理制动/终点回正、停止请求到执行确认是不同阶段；不得把参考Demo在
已停稳后使用的10秒退出确认预算，移作另一算法从高速入圈到完整停稳的预算。
同时核查参考任务的observe/fail策略，不能暗中对新算法额外强制速度、倾角或边界
门槛后宣称是同标准比较。保留旧轮次原判定，按预声明的统一契约重新验证。

Action已完成时取消请求可能返回空goals_canceling，且最终结果回调仍排在队列中。
不能仅凭“取消未接受且结果future暂未done”判定执行仍活跃；在同一个有界退出预算内
等待最终结果，再核对控制器模式和输出静默。若目标仍活跃且拒绝取消，最终结果等待
必须超时失败。终点停车与断流恢复分别复验；正常到达预算修正不能同步放宽故障停车门槛。

进入目标距离门槛后，分别确认停止服务/执行反馈、控制器模式及新鲜定位下的速度保持时间；到达不能替代停止成功。YOPO 一轮已到达5 m门槛并接受8个滚动revision，但速度未在10 s内满足0.2 m/s连续1 s，仍记为失败。恢复脚本应独立尝试原生 Land，即使取消服务已返回 FAULT/失败；取消失败不能通过同一异常块跳过降落。确认 Land 结果和 disarmed 后才能清理场景/时钟。保留重复 disarm 告警，并区分主动任务通过与事后恢复成功。

原生 Land 的Action成功可能先于内部disarm清理。任务先等待平台解除武装反馈，超时后才补发disarm；already-disarmed服务拒绝必须由实际反馈判定。取消应在STOPPED状态幂等，避免任务清理触发第二次停止并与Land竞争。故障测试暂停ROSCLI包装器时需覆盖它的实际节点进程组；独立传感器容器可用pause/unpause隔离注入，保留PX4和时钟。

若任务要求 landed 与 disarmed，收尾须在既有恢复预算内同时等待目标实例两项新鲜反馈，不假设它们的到达顺序，也不能在其中一项到达时用另一项的旧值立即判失败。记录命令、Action结果、两项状态的接收时刻及各自时钟域；缺项或超时仍判失败。历史反馈顺序见[执行诊断](references/execution-diagnostics.md)，不据案例假定其他固件的反馈顺序或延迟。

多轮隔离复现使用各轮独立DDS域并记录选择依据；起飞前核对clock/定位/状态发布权唯一和时钟单调。相同容器PID不是GUID冲突证据，应读实际GID；本轮探针在PID=1时得到不同GID。复现中一次未知Action/交替时钟的根因未定，保留失败，后续隔离通过不能将猜测升级为确定根因。正常/故障各轮保留独立输出目录。host与容器协作写证据时由host先创建case目录，避免root容器创建目录后host无法写注入标记，导致故障提前恢复。清理必须等待实际退出后再复用端口。

现场观看复跑可使用现有AirSim manager的`AIRSIM_RENDER_MODE=windowed`，从当前图形会话取得显示/授权配置，个人显示地址和授权路径只进本地过程记录。先核实真实场景窗口可见、地面就绪，再告知开始时间并下达任务；保留停止/Land/disarmed证据。用户要求继续查看时可保留解除武装后的窗口与空闲部署，记录本次资源身份和停止入口；现场观看未录屏时不能宣称已生成视频。

长距离任务需依据距离、配置速度与绕行余量设置独立导航等待预算，并记录CLI实际传入值；增加导航超时不改变推理/提交预算、轨迹连续性、定位新鲜度或停止门槛。速度报告区分配置速度尺度与飞行阶段测量值，用同一状态源的速度向量范数统计中位/峰值，注明时间窗口。落地后的AirSim `has_collided`可报告Landscape地形接触；保留对象、时间、法线及原始标志，分别报告飞行障碍碰撞与降落接触，不把原始true静默改为false。

## AirSim Blocks 碰撞门控与会话复用约束（2026-11-16 SPF 教训）

Blocks WindowsNoEditor 的 msgpack-rpc 面与新版 AirSim 客户端不一致：`simGetCameraPose`、`resetLastCollision` 不存在（`rpclib: server could not find function`），`simGetImages` 压缩字节在 `image_data_uint8` 键。调用前用一次探测确认方法可用，不能按 Python 客户端源码假定 RPC 面完整。

`has_collided` 在整个 Blocks 会话粘滞，且 spawn/传送本身即可置位——起飞前基线可能已为 true，正常触地也会置位。因此导航期碰撞门控必须：起飞后采集基线（含 `time_stamp`），任务期间周期轮询，仅当 `time_stamp` 相对基线变化才记为新碰撞事件；绝不在 Land 之后单次查询判 FAIL。2026-11-16 SPF run x/y 曾因"降落后查询"把触地/残留误判为碰撞失败，掩盖了实际成功的导航闭环。

同一 Blocks 会话通常只有第一个 mission 能可靠 arm：完整 land/disarm 后再次 teleport 会触发 PX4 `GPS Horizontal Pos Drift too high` 等 preflight 拒绝并持续数分钟。每个用例应独立 start→mission→stop，不在同会话连续跑多任务；arm 重试循环加退避只能兜底，不消除该约束。

区分"评分缺陷"与"链路缺陷"：门控 FAIL 时先对照原始样本流（状态序列、位置轨迹、收口 reason）判断是链路失败还是评分实现错误。最终 STOPPED 状态必须保留任务计数器（如 cycles_done）——快照在清空内部状态前取值，否则监控端把已完成任务读成零完成。

观察视图随动成功只以任务期间质心序列移动（track.jsonl）加俯视帧为准；`--once` 健康检查仅证明相机存在与摆放连通，静态初始相机姿态不得申报为跟踪成功（AGENTS 要求）。

替代云端 VLM（付费模型不可用时）的失败常表现为 ~2s 内快速回错（空响应/限流），与超时不同：重试必须带退避间隔，连续失败预算相应放宽，并把解析率作为记录指标在跑前锁定口径中声明；事后不得为凑通过率临时改动门槛。

变更起飞高度作单因素实验时，同时记录原生Takeoff请求高度、策略交接时实际位置及独立真值，保留终点与保护门槛；注明相对原任务起点的变化。按空间路段对照航段高度，区分世界高度与离地净空。较高起飞后策略可能回落，单轮通过不能证明高度优势持续或建立起因果关系。交接阶段因状态过期等保护提前终止的轮次保留为失败，另开目录复跑，不将其算作有效航段。

## 姿态与角速度执行验证

从飞行记录做姿态时移拟合时，将其称为动态响应估计，分别核对策略输出、ROS平台设定值发布、固件uORB接收、实际姿态和估计状态的时间；ROS发布点不证明固件已收到。使用原stamp和坐标转换后的旋转矩阵匹配同一指令，避免把发布重采样、纯传输延迟、一阶响应和估计器延迟混为一个量。与训练动态比较前展开动作缓冲的实际索引，参数名为lag=1不保证只延后一拍。连续闭环中的最优时移不能单独证明控制器是避障瓶颈；以独立小幅阶跃/扫频和原保护门槛下的对照飞行验证。PX4开发快照可能包含姿态参考模型，检查锁定提交和运行参数；机型默认值、settings请求值与固件实际值分别记录。AirSim本地源码的电机时间常数也不能替代预编译场景的实测响应。

验证姿态入口时除ROS模式反馈外，采集目标固件的vehicle_control_mode，确认姿态环开启；角速度入口应另验姿态环关闭。记录实际姿态设定值和推力，检查坐标四元数变换（q与-q等价）及归一化；采用时间窗数值匹配时明确不能证明唯一序号对应。原生起飞、短时保持/航向响应、主动取消或断流保持、低速确认及Land/disarmed形成独立用例。

100ms流watchdog在有屏仿真中可能受采集和调度空隙触发。先记录控制帧与时钟的真实间隔，检查执行期首次导入、数值库线程和无关采集负载；仅在测试不消费相机时才可停用相机桥并明确范围，仍保留渲染和实际控制闭环。此类配置下通过不能推广为视觉策略或相机输入已通过，也不宜仅凭前后结果认定唯一根因。

配置对齐可先单独执行不解锁的场景/飞控启动用例：在目标固件就绪后导出实际参数、
机型和vehicle_status，明确没有启动运动客户端，再清理所属资源。
参数快照不等于姿态/推力动态验证。后续飞行也保存同一快照，
避免把settings请求或源码默认误当作该轮实际参数。回查上游物理模型时沿实际launch
追踪到xacro/link及电机插件，分别记录控制器质量参数、机身质量和附加link；
记录物理步长、配置实时因子与实测RTF，不能只比较用户界面的速度倍率。

相同watchdog文本也可能由策略输出被安全校验拒绝造成。先关联decode拒绝、实际求解
往返、原图发布/接收和控制流时间线，再判定是输入/传输时延还是输出不适用。
飞行过早因边界或输出保护结束时，可增加不解锁、不发送运动指令的真实相机/GPU
持续探针以隔离时延；运行前声明时长、调用数、同步和耗时门槛，明确地面探针
不替代空中执行、正常导航和故障收口。ClockSpeed设置与实际RTF分别记录。

## 多速率状态与有屏证据

状态估计同时包含低频全局校正与高频局部控制状态时，先追踪官方下游代码实际订阅的 topic，不能按相同消息类型或近似名称猜测状态源；再分别定义并测量两种 freshness。全局校正间隔反映视觉/SLAM 更新能力，高频传播状态、canonical pose、twist 和 TF 间隔决定控制可用性，不得用较宽的全局门槛替代控制门槛，也不得给旧关键帧重新盖章制造高频输出。频率证据使用专用轻量订阅器记录到达时间和消息时间；订阅全部高带宽话题且自身过载的采集器漏消息时，不能据此判定发布端不新鲜。

单目或其他需要运动激励的估计器不能在悬停中直接等待“就绪”后注入故障。故障场景先执行预声明的可观测运动，确认算法已进入有效跟踪且对外输出被实际消费，再写入注入就绪标记。注入后分别记录目标流停止耗时、canonical 保持期间的新样本数、从注入到降落解除武装的总恢复耗时；不能把整个降落时间误写成故障检测延迟。

有屏验收同时记录启动参数、显示环境、窗口身份和场景画面。窗口存在且未启用离屏渲染只能证明图形进程与窗口链路；桌面锁定时截到锁屏不能声称为可见场景截图，应如实保留限制并用真实传感器数据等其他证据证明该轮算法输入。

## 移动车辆的地面 Mission 观察

观察链可在不解锁的 AirSim/PX4 场景中独立验证：真实 RGB-D → CUDA 检测 →
Tracking Action → 实际 Mission 跟随点日志。运行前声明完整观察时长、不同 capture ID
及采样 stamp 的最少数量、移动距离、几何和自身高度误差、失跟规则及清理条件。
数量/位移子项通过后提前失跟仍为整轮失败；不缩短时长或扩大预测有效期换取通过。
真值仅用于独立评分和明确授权的测试初态，不能替代 ROS 感知或自身状态。

Mountains 车队使用场景内路线与自定义启停 RPC。独立 UserDir 要携带路线存档，
不能只换 Shipping 二进制。记录真实地面相机画面，不把课程起飞后可见性当作地面
可见性。停止 ACK 后采集各车实际速度并满足预声明连续窗口，再清理本轮所属场景；
probe 超时/退出时宿主也需执行有界停车确认。保存既有容器 ID 与启动时刻，收尾核查
未受影响。仓库入口 `deployment/target_tracking/airsim/mountains/` 已在真实场景运行；
移动 Mission 的整轮通过状态以其 VALIDATION 记录为准。


## 起飞取消与降落证据

原生Takeoff接受且PX4检测起飞，不等于Takeoff结果成功或悬停通过。取消未完成的
Takeoff可能令AS2进入EMERGENCY，使原生Land因状态机拒绝；仍独立尝试Land并保留
拒绝证据。PX4随后failsafe/RTL落地解除武装，只能算恢复到地面，不能记原生Land通过。
Mountains固定镜像实例已实际出现此序列，后续诊断不得延长预算或降低高度门槛来
改判旧轮次。飞行原因未定时分别列出观测、假设和缺失证据。

独立恢复节点可能在定时sample之后收到最后的land/mode，故最终disarmed_ground事件
应保存同一时刻完整fresh状态快照；只看最后一条flight-live可能遗漏确认依据。
landed/disarmed与估计速度停稳分别报告；估计器仍漂移时不能宣称实测稳定悬停或停车。
完成确认后清理所属资源，并核对既有容器ID/StartedAt；历史KEEP_RUNTIME文件不代表
当前仍有运行时，接管时必须重新检查实际进程与Docker状态。

## 起飞受阻的物理交叉核对

高度平台期先对照同一时间窗的原生 Action、PX4参考、估计高度、AirSim实际位姿
和逐时碰撞对象/法线/时间戳。`has_collided`可能保留地面历史接触，必须区分起飞后
新顶部接触与正常桥面/地形接触；真值仅作评分，不反馈替换飞控状态。
Mountains中出生点位于装甲车底部，实际仅爬升约0.35m但估计达到约2.5m；
初态ECC_Visibility向上射线全部通过，却未覆盖动态车辆的实际物理碰撞。
因此可见性射线不能单独证明动态障碍净空。修复场景初态后，先独立验证原生
Takeoff3m、原门槛悬停、Land和landed/disarmed，再启动目标观察/移动场景。

该入口 `deployment/target_tracking/airsim/mountains/run.py --flight-only` 支持独立门，
`evaluate_flight.py <运行目录>/probe` 对实际physics-samples与原生结果评分；
`--scene-audit-only`不启动飞行动作，但其可见性射线只作辅助证据。
物理出生点或相机变更需保存解析后的settings及相机pose；静态目标被画幅截断时
先修正实际相机几何与同源TF，不修改检测阈值或跟踪门槛换取通过。

侧视几何审查应在等待 PX4 Ready 日志前保存原图、原始字节、pose及碰撞，
以免地面出生点碰护栏导致 readiness 超时后丢失关键证据。保留水平护栏接触
失败轮次；只在修正地面设置并通过独立原生飞行门后开始观察。
静态门记录每次不同 stamp/capture 数量、位置spread及逐谓词时间；
无目标时按无有效观测报告，不将空集合的运动/几何指标判为通过。
采样TF应由实际消费者 Buffer 在清理前导出；临近容器停止才启动 ROSCLI
可能没有数据，空文件不构成TF证据。Mountains侧视复核用同配置重跑补齐
实际TF，但两轮仍无受支持类别框，因此静态失败、车队未启动、移动未执行。

## 限定范围的离线 Inference Engine 验证

用户明确只授权 Engine 与保存的真实图片时，运行前将输入回放、direct 模型全输出
数值对照、真实 CUDA HTTP、独立 ROS 客户端/Adapter 往返、错误/超时和清理列入矩阵；
实时传感器、Tool、Tracking、场景启动和飞行保持范围外，不为补齐平台闭环擅自启动。
组件保持 partial，准确报告 Engine 已通过层级。保存图片本身不能证明采集 header；
回放测试明确提供测试 stamp，验证保留语义，不假称恢复了原始采样时间。

数值对照至少保留全部原始 tensor 和全部后处理框/评分/短语，阈值在运行前固定。
完全不透明 RGBA 转 RGB 时保留全幅和全部 RGB 像素，并分别记录原文件哈希及转换。
计时分开记录 direct forward、worker 分项、HTTP 往返、DDS 往返；约百毫秒 GPU 推理
可同时出现秒级完整图像 DDS 传输，不用 GPU 时延代替实际服务时延，也不事后补设
性能通过门槛。取消真实 HTTP 调用后观察 busy，验证重复请求得到429、完成后恢复；
另用确定性 runtime 测试覆盖取消期间持有执行槽和关闭释放。


## Detect 到 Tracking 的保存数据回放

在只授权静态回放时，可用真实 CUDA Engine、Tool、AS2 Module 和 Tracking Action
验证消费链，无需启动场景或飞行。分别记录真实 RGB/深度文件、录制 TF 与测试
stamp 的来源；同进程真实 DDS 与跨容器/跨设备证据分开。对比 Engine 全部实际框与
Tool 返回框/短语，不用 query 文本替换模型标签。用确定性 ROS 服务另验 query/phrase
不一致、空短语、版本/世代变化、超时并发、取消与迟到隔离。

真实框存在但深度 policy 拒绝时，预期为二维成功/PARTIAL 和 Tracking 不可用；
不能把 Action 窗口 TIMEOUT、反馈数量或有效框当作三维跟踪通过。Detect query 本轮
保存皮卡在真实 CUDA 上检出 car，但竞争深度簇使三维无效；相应回放只证明接口及
保护行为，实时传感器、三维精度、移动目标与飞行仍未完成。

Demo 后端切换可先分别运行启动计划、实际参数文件的 ROS 节点构造、原有消费者
回归和保存数据 CUDA 回放；静态回放通过后，实时观察与显式悬停仍各自待验收。
Fast DDS 默认端口计算下，domain 233 已实测超限，隔离域必须在当前中间件支持范围
内选择并核查占用；保留启动失败日志，另用有效域重跑，不记成算法失败或跳过。
相机诊断依赖检查在启动场景前完成，避免模型环境更换后宿主缺少图像库才中途失败。


## 实时框深度拒绝的证据边界（2026-11-16）

静态门失败时，即使原生起降、相机TF和真实GPU检测均通过，移动阶段仍标为
未执行，总体未通过。Mountains受控俯视实测25次检测均有框而全部三维投影拒绝；
因此不能将“目标清晰入镜”替代至少四个不同有效三维采集的前置门。
诊断保存每次投影实际使用的深度、框、内参和采样TF及身份；稍早的手动截图/深度
与后续推理框不能当作同帧配对。若既有采集只保存推理RGB与投影错误，应明确该
缺口，不能用文件序号强配截图来计算精确的逐调用深度簇指标。出生点变更另核对
实际地形与目标可见性：相对3m起飞成功不证明仍在原桥面或目标视野中。

## 识别人和尺寸先验测距的阶段门

WestStreet/ProjectAirSim 的人物识别与测距分开判定。实际 YOLO 可在暂停和跑步画面
均检出 person，而深度定位分别只有5/6和2/6有效；静态 success 不代表动态测距通过。
逐阶段记录唯一 RGB stamp、检测数、有效三维数、同步拒绝与测距范围拒绝。

用户选择尺寸先验后，用显式 position_method 与名义高度区分深度测量；记录完整框、
内参、RGB采样时刻TF、先验高度及其误差来源。人物跑姿改变可见高度，不能把固定
身高当作精确真值。拒绝截断框、不适用的俯视角和无效几何；尺寸先验的单元测试或
真实检测框回放不替代实时ROS、Tracking消费与飞行验收。
若回放仅有配对depth时刻的TF，应注明与RGB的偏差，不称其为精确RGB采样TF证据。


尺寸先验与人物真值核对时，先统一距离定义：光轴Z、水平距离和三维距离不可混比；
Actor根位置与身体中心也不可直接混用。简单检查可比较相机到人物的水平距离，
独立原生机体真值加实际相机外参得到相机位置；估计端仍用图像时刻TF。
真值记录独立于算法输入，按最高置信度等预定规则选框，不能按真值挑选正确框。
只读RPC若非图像原子采集，用仿真时间前后夹取并报告间隔、插值方式和速度对应的
时间不确定度，拒绝跨reset/启停状态和大间隔。固定名义身高先验先评分；
如需用真值校准，校准与验证必须使用不同采集，不能将同批拟合误差作为验收。

## System Tool 的平台准备服务与状态暂停

锁定 AS2/PX4 的解锁、模式切换服务可能同步等待飞控确认，期间平台与定位发布
暂停。WestStreet 实测约1.2s，能触发0.75s状态门。不要直接增加运行期新鲜度阈值：
对已经提交的原子准备服务先等待明确结果，再重新获取原门限内的新鲜状态，之后
才允许发起运动 Behavior。取消时同样先收口已提交服务并检查物理状态；无法确认
仍保留占用。对“服务暂停超过状态门”和“服务中取消后回滚”分别做ROS回归，
再以真实 System起飞/降落确认；PX4独立恢复不等于Tool成功。

ROS bag录制期间避免对同一个SQLite库启动长读取事务，否则可能阻塞写入并导致
recorder以database locked退出。结束录制后再分析，或分析一致性副本；运行期诊断
用独立轻量订阅器。保留录制异常，缺失证据不能由任务返回成功补齐。

## 相同图像的分段耗时诊断

按原始采样stamp连接采集回调、隔离放行/丢弃、buffer入队/取出、模型服务往返、
测距和下游消费，分别记录单调/墙钟/ROS时间及事件seq；像素采样间隔不是推理
调用间隔，更不是计算耗时。同宿主容器可比较单调时钟，跨设备先测偏差。
明确最早打点边界：原生ROS回调不是渲染/曝光时刻。发布事件没有对应接收回调时
只定位到该传输/接收/调度区间，不直接称网络丢包。区分初始化/会话外长尾与实际
Tracking消费帧，检查诊断事件自身是否缺失；把首次失效逐帧去向与全轮最大间隔
分开报告。缺测、测距/关联拒绝和云台隔离可能共同造成失效，不能凭单个间隔归因。

图像传输溢出诊断区分UDP datagram drop与完整RGB丢帧，不按数量直接换算。
当DDS请求缓冲与SO_RCVBUF不符，记录host上限、实际socket值与inode累计drop。
单变量临时系统参数A/B须保存原值、运行前后值并在finally恢复，不写持久sysctl；
启动器要求新建证据目录时，A/B外层元数据放目录外，避免预创建目录使整轮未运行。

传输修复后应保持原连续任务预算重新验证，不能把短轮成功推广为长轮可靠。
观测持续到达但Tracker失跟时，重放同一会话原始测量，分别记录平滑输出、预测
位置/速度、欧氏残差、创新分数及实际拒绝门。平滑生效不等于关联通过；多重门中
创新分数通过而硬距离门拒绝时需明确指出。运动噪声候选只在原失败片段通过、
或造成不合理速度估计时，保持未验证，不直接上线或放宽失跟门改判。

目标平滑启动验证通过后，用原连续任务预算做独立实测；启动平滑不能替代尺寸
测距抗噪验证。记录首个valid到首个invalid的实际持续时间、目标更新覆盖、实际
无人机位移和执行参考，分别报告。局部历史修复后再次失败时核对新拒绝链，保留
有效观测采样时间、失效时刻及后续恢复结果的处理时刻；晚到恢复不改判已触发的
任务失败。不要靠重复同参数飞行或扩大失效时间将局部改善写成长期通过。

验证软降权/限幅策略时，记录实际权重、增益缩放和修正大小；若真实飞行在正常
更新阶段被其他组件提前中断，权重始终为1，则只覆盖正常分支，不能据“未失跟”
证明噪声分支可靠。保留独立回放与真实飞行证据等级，先定位新的执行阻塞点再复测。
执行修改服务仅返回布尔拒绝时，不从附近警告直接推定连续性/时序根因，也不默认
重试或忽略；核对执行生命周期、修改请求、终态与精确拒绝原因。

终点轨迹的滚动更新被拒绝时，先比较最后已提交覆盖终点、新曲线原起点与实际
valid_from。旧final已结束而新计划无时间重叠，是新执行阶段，不能靠增大PVA
连续性门限或重定时修复。HOLD任务可经已有停止确认后重新接管，保持同一任务
和资源所有权，并缓存交接期间最新目标；非final断流仍需失败收口。用原录包时间
驱动实际Timeline及Adapter调用边界回归，验证重叠仍修改、非重叠final交接、取消
与非托管失败。旧轮缺服务端分支记录时区分“可证明的契约违反”和“未知的具体
return”；后来自然场景通过但分支计数为0，不提升为该故障分支实飞覆盖。

Adapter自动将更新路由至新Action时，必须区分“确认成功完成”与泛化的modify拒绝：
后者还可能是取消、失败、过期或连续性错误，不能一概自动重启。测试覆盖新目标
到达/新计划排队时旧执行完成、相同目标续期、停止确认延迟期间连续更新、取消优先，
确认新Action使用最新目标且外层任务与资源所有权不变。受控执行double的真实ROS
协议通过与真实PX4任务门分别报告，不以其中之一替代另一项。

转弯追踪验收先用路线时间/真值确定首个路口，预算必须实际覆盖路口及其后续段；
20秒直线成功不能推断约21秒后转弯成功。独立记录人物姿态/时间用于评分，
不反馈Tool任务。缺测时查看原图：人物仍可见但框很小、YOLO连续空检测，
与图像停止、关联门拒绝、相机转出画面分开判定；云台靠近限位不单独证明根因。

需要保留观察窗口时预声明keep-scene：物理解除武装确认后停止执行服务，
记录所属场景/PX4/桥接/relay。报告执行清理与场景保留，不能说全部服务停止。
System Land超时但PX4已disarm仍是降落失败，不因可安全保留场景而改判通过。
复用场景须同时核查原生Pair0 relay与bridge的所有权，不能盲启第二个relay。

检测调试小窗优先复用实际推理输入与结果，按采样stamp精确关联，而非把
旧框贴到最新原生画面。回放必须显式标REPLAY；实时显示最新已完成结果，
无新结果标STALE。窗口独立读取证据，不增加原生Pair0订阅或推理调用。
WestStreet yolo_viewer.py提供该观察入口；真实回放通过不等于实时闭环验证。

目标朝向接入必须对齐“调用目标yaw、Behavior实际输出参考yaw、实测机头yaw”
三层时间，不能看到目标pose已接受就把转向滞后归因飞控。SUPER原生goal_yaw
可为末端朝向约束，滚动重规划可能持续推迟转头；接口支持不等于持续盯人。
转弯失跟逐帧核对框位置与裁边、最后有效测量及缺测到期，分开报告感知耗时。
WestStreet实飞出现目标44.9度、参考3.4度、实测1.81度，说明主要滞后
已在参考层出现；该任务失败不能由正常Land/disarm改判通过。

持续yaw与位置规划解耦时，仍须保持一个执行器/一个控制出口。验证初始
任务中的yaw策略与轨迹yaw互斥、独立更新不等待新位置轨迹、位置滚动不
重置yaw状态、目标版本递增和任务身份、过期/取消后迟到请求不能复活动作。
接口扩展后重编译所有受影响overlay，不混用旧Behavior与新TimedPath。
角速度及角加速度限制会带来响应时间，反向测试须区分制动阶段与未响应；
不要为了测试通过去掉限制。实飞参考变快但机头仍滞后时，继续对齐目标、
参考与状态，再决定预测/平滑或下游控制调整，不把接口完成写成跟踪成功。

短时失检恢复窗口的预算要包含采样间隔与处理/传输到实际消费的延迟。
恢复帧采样早于截止，但结果晚到仍可能已经失效，不能用采样时间单独
判恢复成功。实验前声明窗口及预测期运动策略；原失败轮保留结论，再
按测量依据提出独立候选，禁止在同轮放宽门限重判。预测窗口延长时保留
原始observation_stamp、输入新鲜度和关联/更新限幅预算，避免隐含多变量。

观察窗应由启动fixture持有Popen句柄，任务结束/异常finally关闭；保留
仿真场景不等于保留YOLO窗口。显示进程处理SIGTERM并退出其官方显示
子进程，另可设置无数据idle期限。分别用正常空闲退出和SIGTERM实际GUI
测试检查子PID无残留，不用全局pkill。历史残留仅在核实命令/进程组归属后
清理，不影响其他容器或编辑器。


路线绕障试验分别报告追踪段与降落段接触。以实际任务起止/取消和
Land调用边界区分阶段；Land完成时间之前的所有接触不全是追踪碰撞。
WestStreet首弯延后4m的35秒任务已通过，但降落高度约0.13m时接触
路沿，碰撞audit仍失败，不能因任务success或disarm而宣称全程无碰撞。
同时保留原始接触日志、位置/速度、阶段时间依据和审计失败结论。

候选跟随点的离线rollout仅为筛查：必须标出其加速度/速度/转向响应假设，
再对齐真实执行参考、实际机头与图像裁框。直接按yaw限速更新简化状态
不代表真实机头能达到该响应；距离已回升也可能因视线转动过快而失跟。
以历史自身状态进行的反事实选点，不能当作候选策略闭环效果或可见性通过。
WestStreet候选点首轮在第二弯约50秒仍裁框失跟，保持失败与默认关闭，
不能靠增加候选、放宽测距/跟丢门把未校准模型变为可行性保证。

恢复窗口与恢复入口是不同变量。窗口只规定何时失效，入口决定
何时冻结/减速；入口接近正常采集处理年龄会反复误触发。以独立轮次
对比冻结占比和任务持续时间，不因冻结次数下降就宣称解决失跟。
WestStreet p/v跟随1秒窗口＋0.3/0.6秒入口分别约29.44/29.37秒失败，
冻结26/96降至3/95，仍因远处约29px人物连续漏检。需核对实际距离
和下游运动，不能反复延长有效期；保留样本时间＋结果到达的完整预算。

固定真实漏检序列做检测对照时，先用实际部署Predictor/相同权重在CUDA
重推默认输入，逐帧比较录制输出；阈值与ROI分别对照。ROI种子来自
序列开始前已接纳检测，更新只用已完成帧，禁止用当前真值或未来检测
裁剪。报告检出采样最大间隔、同目标重复框、有限无人背景对照与
实际调用耗时，分别标出人工审阅、离线回放及尚未验证的闭环。
WestStreet33帧默认8、因果256px ROI28、最大间隔1.002降到0.252秒，
仅为保存帧证据，不能提升为跟踪或飞行通过。

移动后方参考增加p+v·lead时，将lead显式配置并保持默认，分开验证
参考速率限幅和真实下游运动；位置前看不是终端速度/轨迹前馈。
WestStreet显式1秒lead通过65秒，但240秒在78.8秒柱墩遮挡失效；
成功短轮后应继续原目标长轮，原图分别判定“中央可见但漏检”和
“被实体遮挡”，不能用相同lost结果混归因。偶发执行错误可在确认
清理后同配置重试，保留失败，不用多次重试抹去新场景限制。

## 验证器不得制造被测断流

证据节点订阅高频 BEST_EFFORT/SensorDataQoS 流时，不要在同一单线程 executor 回调路径串行执行截图、文件编码、AirSim RPC、真值查询或统计排序。阻塞期间队列可能覆盖样本，产生看似来自系统的 0.2--0.3 s gap。ROS executor 与耗时证据采集分线程，重计算放在运行后；用源 header stamp 和本机 monotonic arrival 同时记录，分别回答采样时间连续性与接收实时性。

freshness gate 只统计预声明的有效窗口，例如起飞后到降落前；初始化阶段仍作为 readiness 证据保留，但不能混进飞行 gap。仿真 `/clock` 可能步进或暂停，wall arrival 不能代替 source stamp，source stamp 也不能证明 observer 实时收到。若修正验证器改变 manifest，应生成新的 shadow 证据，再让 authority gate 比较同一运行时代码、镜像、上游提交和标定；不能通过忽略整个启动脚本哈希复用旧证据。
